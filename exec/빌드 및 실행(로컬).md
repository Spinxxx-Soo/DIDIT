# 4. 로컬 빌드 및 실행

## 4.1 로컬 빌드(백엔드/프론트/AI/도커)

### 4.1.1 Host(로컬 PC) 빌드

#### (1) 백엔드(Sprint Boot)

1. 이동
    

```bash
cd apps/server
```

2. 빌드(테스트 제외)
    

```bash
./gradlew clean build -x test
# 또는
./gradlew clean bootJar -x test
```

#### (2) 프론트엔드(Vite)

1. 이동
    

```bash
cd apps/client
```

2. 의존성 설치
    

```bash
npm ci
```

3. 빌드
    

```bash
npm run build
```

#### (3) AI 서비스(FastAPI)

- 별도 빌드 산출물은 없으며, **의존성 설치**로 준비한다.
    

1. 이동
    

```bash
cd apps/ai
```

2. 가상환경 생성/활성화 및 의존성 설치
    

```bash
python -m venv .venv
# Windows
.venv/Scripts/activate
pip install -r requirements.txt
```

---

### 4.1.2 Docker 이미지 빌드

#### (1) 백엔드 이미지

```bash
docker build -t didit-server:local apps/server
```

#### (2) 프론트엔드 이미지

```bash
docker build -t didit-client:local apps/client
```
    

---

## 4.2 로컬 실행 절차(구성요소 기동 순서)

### 4.2.1 Host 기반 실행(개발 모드)

**권장 순서:** 인프라(DB/Redis/OpenVidu) → 백엔드 → AI → 프론트엔드

#### (1) 인프라 기동(DB/Redis/OpenVidu)

```bash
docker compose --env-file apps/server/.env -f apps/server/docker-compose.yml up -d
```

#### (2) 백엔드 실행

```bash
cd apps/server
./gradlew bootRun
```

- 환경변수는 OS/IDE에서 주입하거나 기본값을 사용한다.
    

#### (3) AI 서비스 실행

```bash
cd apps/ai/src
uvicorn api.main:app --host 0.0.0.0 --port 8000
```

#### (4) 프론트엔드 실행(개발 서버)

```bash
cd apps/client
npm install
npm run dev
```

---

### 4.2.2 Docker Compose 기반 실행(전체 스택)

> 배포용 Compose를 로컬에서 실행하려면 `.env`와 네트워크 조건을 충족해야 한다.

#### (1) `.env` 준비

- `infra/docker-compose/.env`에 필요한 환경변수를 정의한다.
    
    - 예: `MYSQL_ROOT_PASSWORD`, `MYSQL_USER`, `MYSQL_PASSWORD`
        
    - 예: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`
        
    - 예: `OPENVIDU_*`, `REDIS_*`
        

#### (2) 네트워크 확인

- `infra/docker-compose/docker-compose.yml`은 **`caddy_default` 외부 네트워크**를 참조한다.
    
- 로컬에서 사용할 경우 다음 중 하나가 필요하다.
    
    - 외부 네트워크 생성
        
    - 또는 compose 파일의 네트워크 설정을 로컬 환경에 맞게 수정
        

#### (3) 전체 기동

```bash
docker compose --env-file infra/docker-compose/.env -f infra/docker-compose/docker-compose.yml up -d
```


### 4.2.3 이미지 레지스트리 관련 

- `infra/docker-compose/docker-compose.yml`은 서버/클라이언트 컨테이너를 **레지스트리에서 pull**하는 구성을 기본으로 한다.
    
- 현재 프로젝트에서 사용되는 컨테이너 이미지 저장소가 **Private 레지스트리(비공개 저장소)**인 경우, 로컬 환경에서는 다음 중 하나의 조치가 필요하다.
    

#### 옵션 A) 로컬에서 빌드한 이미지를 레지스트리에 업로드 후 사용(권장: 운영과 동일)

1. 로컬에서 이미지 빌드
    
    - `didit-server:<tag>`, `didit-client:<tag>` 등
        
2. Private 레지스트리 로그인 후 push
    
3. `infra/docker-compose/docker-compose.yml`의 `image:` 값을 **업로드한 이미지 태그로 변경**(또는 동일 태그 유지)
    
4. `docker compose up -d`로 기동
    

#### 옵션 B) 레지스트리 pull 대신 로컬 빌드로 대체(로컬 검증용)

- `infra/docker-compose/docker-compose.yml`에서 각 서비스의 `image:`를 사용하지 않고 `build:` 설정을 추가하여 로컬 빌드로 실행하도록 변경할 수 있다.
    
- 단, 이 방식은 운영 배포 방식과 차이가 생길 수 있으므로 **로컬 검증 목적**으로만 사용을 권장한다.
    

#### 옵션 C) 레지스트리 접근 권한을 부여받아 pull 수행

- Private 레지스트리에 대한 계정/토큰 권한이 있는 경우 `docker login` 후 pull 기반 실행이 가능하다.
    

> 결론적으로, **Private 레지스트리인 환경에서는 “로컬 빌드 → 레지스트리 업로드 → compose 이미지 참조 변경(또는 동일 태그 유지)” 절차가 필요**하다.
